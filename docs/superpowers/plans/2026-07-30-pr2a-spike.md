## Q1 — Is `entry.colIdMap` fully populated for every column of the element at the time the relationship loop runs, or only for columns already referenced elsewhere?

**Answer: fully populated for every column the element was built with, before the
relationship loop runs at all.**

For each `rel` in `childRels` (each Tableau logical table), the converter builds
`columns`, `order`, and `colIdMap` for that element in a single pass
(`converter/tableau.mjs:4741`–`4810`), then stores the result in `elementMap`
(`converter/tableau.mjs:4808`). That entire per-table loop completes — for *every*
table — before the relationship loop even starts reading `<object-graph>`
(`converter/tableau.mjs:4811`: `const objGraph = nsChild(ds.ds, "object-graph");`,
sequentially after the loop closes at `4810`).

Two population paths run inside that build loop, and one always fires per table:
- If Tableau serialized `<metadata-records>` for the table (the common case), a
  `for (const { uuid, caption, ... } of metaCols)` loop (`converter/tableau.mjs:4762`–`4776`)
  writes every metadata-record column into both `columns` and `colIdMap`.
  `metaCols` itself is sourced from `metaByObjId`/`metaByParent`
  (`converter/tableau.mjs:4711`–`4737`), which bucket *every* `class="column"`
  metadata-record under the connection — not a subset limited to columns used
  elsewhere in the workbook.
- Fallback, only when `metaCols.length === 0`: a loop over the relation's own
  `<columns><column>` elements (`converter/tableau.mjs:4777`–`4792`) writes each
  one into `columns`/`colIdMap`.

`ensureCol` (`converter/tableau.mjs:4841`) is the *only* thing that adds entries
to `colIdMap` after this point, and it is defined and invoked only inside the
relationship loop's per-relationship body (`converter/tableau.mjs:4895`–`4896`),
never before. It only fires when a specific serialized join-key reference (an
`op` attribute in a `<expression>`) isn't already in the pre-built map — i.e. it
supplements a genuinely absent column (e.g. one Tableau references only via a
relationship expression), it does not "fill in" the main enumeration lazily.

**Conclusion:** `colIdMap` at the moment the relationship loop runs already
reflects the element's full declared column set (per whichever of the two build
paths fired) — it is safe to enumerate for inference.

## Q2 — What exactly are `entry.colIdMap`'s keys? List every form written.

Keys are always plain-object string keys, one id per column, written as multiple
aliases pointing at the same `id`. Forms written, by site:

**metaCols path** (`converter/tableau.mjs:4772`–`4775`), for each column:
- `uuid.toUpperCase()` — the Tableau GUID, uppercased (`:4772`)
- `uuid.toUpperCase().replace(/-/g, "_")` — the GUID with dashes swapped for
  underscores (`:4773`)
- `cleanCaption.toUpperCase()` — the display caption (trailing `(...)` suffix
  stripped), uppercased, **spaces preserved** (`:4774`)
- `cleanCaption.toUpperCase().replace(/\s+/g, "_")` — same caption, uppercased,
  **spaces turned into underscores** (`:4775`)

**Fallback path** (`converter/tableau.mjs:4789`–`4790`), for each column:
- `rawCol.toUpperCase()` — the raw `name` attribute off `<columns><column>`,
  uppercased (`:4789`)
- `key`, where `key = isUuid ? rawCol.toUpperCase() : normalizeColumnName(rawCol)`
  (`:4781`, `:4790`) — `normalizeColumnName` (`converter/tableau.mjs:3681`-`3683`)
  collapses *every* run of non-alphanumeric characters (not just whitespace) to a
  single underscore, trims leading/trailing underscores, and uppercases.

**`ensureCol`-added supplementary keys** (`converter/tableau.mjs:4853`, `4855`-`4856`),
only for keys absent from the above:
- the literal lookup `key` passed in (an uppercased physical-column op-ref or GUID)
- if the key was a GUID with a known caption (`guidCaption`, `:4846`): `cap.toUpperCase()`
  and `cap.toUpperCase().replace(/\s+/g, "_")`

**Caveat:** all of these are plain assignments (`colIdMap[k] = id`) with no existence
check, so if two distinct columns on the same element normalize to the same key
form, the later write silently overwrites the earlier id (see RISKS).

## Q3 — Does `entry.element.columns` hold the FULL column set for a warehouse-table element at that point? What's the reliable way to get a column's display name?

**Answer: yes.** `entry.element.columns` *is* the same array reference (`columns`)
built by the identical loop that populates `colIdMap` — pushed to at
`converter/tableau.mjs:4770` (metaCols path) or `:4787` (fallback path), then
assigned into `el = { id, kind: "table", source, columns, order }`
(`converter/tableau.mjs:4807`) and stored as `elementMap[fullName].element`
(`:4808`). There is no separate, narrower "full schema" source — this is it, and
it is exactly what `colIdMap` was built from, so the two structures agree by
construction. (It reflects everything Tableau *serialized* metadata for or listed
in the relation's own `<columns>` — not necessarily literally every column
physically present in the warehouse table if Tableau never discovered/used one;
see RISKS.)

**Display name — no single property is reliable; a fallback chain is required:**
- metaCols-path columns carry an explicit `name` property
  (`converter/tableau.mjs:4770`: `{ id, formula: ..., name: cleanCaption }`).
- Fallback-path columns do **not** carry `name` at all
  (`converter/tableau.mjs:4787`: `{ id, formula: ... }` — no `name` key) — the
  display name only exists embedded in `formula`, shaped
  `` [Prefix/Display Name] `` (built from `sigmaDisplayName(key)` or a raw
  caption at `converter/tableau.mjs:4786`).

The codebase already has an established idiom for this exact fallback, reused in
many places (e.g. `converter/tableau.mjs:5154`):
```javascript
const nm = c.name || (typeof c.formula === "string" && (c.formula.match(/\/([^\]]+)\]$/) || [])[1]);
```
This is the reliable, already-proven way to get a column's display name from
either shape of column entry — prefer it over inventing a new parse.

## Q4 — How to test whether a column already exists on an entry WITHOUT creating it via `ensureCol`?

`ensureCol` (`converter/tableau.mjs:4841`–`4860`) itself performs exactly this
check on its first line before deciding whether to create anything:

```javascript
// converter/tableau.mjs:4842
let id = entry.colIdMap[key] || entry.colIdMap[key.replace(/-/g, "_")];
```

Everything from `converter/tableau.mjs:4843` (`if (!id) { ... }`) onward is the
**creation** branch — it is skipped entirely whenever this lookup returns a
truthy id. Since `colIdMap` values are always non-empty id strings from
`sigmaInodeId` (`converter/tableau.mjs:2177`–`2180`, never falsy), a plain
truthiness check on a `colIdMap` property lookup is a safe, side-effect-free
existence test:

```javascript
const hasCol = (entry, key) => Boolean(entry.colIdMap[key] || entry.colIdMap[key.replace(/-/g, "_")]);
```

This is a plain object-property read — it never mutates `entry.colIdMap` or
`entry.element.columns`, unlike calling `ensureCol` with a name that turns out
not to exist. Task 2 must call this (or an equivalent bare lookup) for a
*guessed* inference candidate, and only fall through to `ensureCol(entry, key)`
to fetch the id once existence on **both** sides of the relationship has already
been confirmed this way (at which point `ensureCol` is guaranteed to take its
lookup branch, not its creation branch).

## Q5 — Does a case/underscore-normalized display-name index from a prior patch exist, and is it in scope at the relationship loop?

**It exists, but it is out of scope at the relationship loop.**

`converter/PROVENANCE.json`'s `local_patches[0].changes` confirms the prior patch
by name: *"calc flexibility: bare-ref case-fold — case- and underscore-normalized
display-name indexes so bare column references resolve across tables regardless
of casing."* The index it describes is built at
`converter/tableau.mjs:5577`–`5591`:

```javascript
// converter/tableau.mjs:5577-5591
const globalColMap = {};
const displayNameMap = {};
for (const el of elements) {
  for (const c of el.columns || []) {
    const fm = c.formula.match(/\/([^\]]+)\]$/);
    if (fm) {
      const dn = fm[1];
      globalColMap[dn.toUpperCase()] = { elId: el.id, displayName: dn };
      displayNameMap[dn.toUpperCase()] = { colId: c.id, el };
      displayNameMap[dn.replace(/\s+/g, "_").toUpperCase()] = { colId: c.id, el };
    }
    if (c.name)
      displayNameMap[c.name.toUpperCase()] = { colId: c.id, el };
  }
}
```

**Why it's out of scope:** the `relType` dispatch is a flat `if`/`else if` chain —
`"table"` (`:4538`), `"join"` (`:4557`), `"collection"` (`:4706`, closes `:4950`),
`"text"` (`:4951`). `displayNameMap`/`globalColMap` are declared with `const` at
`:5577`–`5578`, textually **after** that entire chain closes, in shared
post-processing that runs once per datasource over the *global* `elements` array
(all tables from whichever branch fired). The object-graph relationship loop
(`:4811`–`4915`) executes entirely inside the `"collection"` branch, strictly
*before* `:5577` is ever reached in the same function invocation. A `const`
declared later in the same block is in the temporal dead zone until its own
declaration — the relationship loop cannot reference `displayNameMap` or
`globalColMap`; they do not yet exist at that point in execution.

**Consequence for Task 2:** don't reference `displayNameMap` — it isn't reachable.
Instead, replicate its exact technique locally within the object-graph loop (same
formula-parse regex, same two case/underscore-normalized forms), so the result is
consistent with how the rest of the bundle already resolves bare column
references. Do not invent a different normalization.

## CHOSEN APPROACH

**(a) The candidate set of an entry's existing column display names:**

```javascript
const candidateNames = (entry) =>
  (entry.element.columns || [])
    .map((c) => c.name || (typeof c.formula === "string" && (c.formula.match(/\/([^\]]+)\]$/) || [])[1]))
    .filter(Boolean)
    .map((nm) => String(nm).replace(/\s+/g, "_").toUpperCase());
```

This reuses the exact display-name-extraction idiom already proven at
`converter/tableau.mjs:5154` and the exact case/underscore-normalization already
proven at `converter/tableau.mjs:5155` and in the prior patch's `displayNameMap`
(`:5586`) — the same transform, replicated locally because `displayNameMap`
itself is out of scope here (Q5). The normalization to apply is exactly:
`String(name).replace(/\s+/g, "_").toUpperCase()` — uppercase, whitespace
collapsed to a single underscore. This matches the key form `colIdMap` itself
stores for caption-derived columns (`:4775`) and is what `normalizeColumnName`
(`:3681`) also converges to for names whose only non-alphanumeric characters are
spaces (the overwhelming common case for column display names).

**(b) Testing whether a given (already-normalized) name exists on an entry
WITHOUT creating it:**

```javascript
const hasCol = (entry, key) => Boolean(entry.colIdMap[key] || entry.colIdMap[key.replace(/-/g, "_")]);
```

This is `ensureCol`'s own existence check (`converter/tableau.mjs:4842`) lifted
out, with the creation branch (`:4843`-`4858`) omitted. It is a pure lookup —
never mutates `colIdMap` or `element.columns`.

**Putting them together for inference** (auto-match / computed-only branches):
name-inference must intersect `candidateNames(firstEntry)` and
`candidateNames(secondEntry)`, then re-verify each intersecting name with
`hasCol` on *both* sides before treating it as a real key component (the
intersection alone is enough given both sides used the same normalization, but
`hasCol` against the real `colIdMap` is the authoritative existence gate — it is
what decides whether `ensureCol` is later called on a name **guaranteed** to
already exist, so `ensureCol` never fabricates a column for a guessed name):

```javascript
const left = candidateNames(firstEntry);
const right = new Set(candidateNames(secondEntry));
const matched = left.filter((n) => right.has(n) && hasCol(firstEntry, n) && hasCol(secondEntry, n));
// matched.length > 1 -> composite key, per the plan's instruction to take ALL matches.
const keys = matched.map((n) => ({
  sourceColumnId: ensureCol(firstEntry, n),
  targetColumnId: ensureCol(secondEntry, n)
}));
```

Secondary fallback (optional, only if the primary whitespace-only normalization
above finds nothing on either side): re-run the same intersection using
`normalizeColumnName` (`converter/tableau.mjs:3681`, already in module scope,
already used to build the fallback path's own `colIdMap` keys at `:4781`) instead
of the inline whitespace-only transform. Prefer the primary form first because it
matches the codebase's own established "bare-ref case-fold" convention (Q5); fall
back to `normalizeColumnName` only to catch caption punctuation the whitespace-only
form wouldn't collapse (e.g. a hyphen).

## RISKS

Flagged for Task 2 to design around — not mitigated here.

1. **Colliding normalized names silently overwrite each other in `colIdMap`.**
   Every write into `colIdMap` (`:4772`-`4775`, `:4789`-`4790`, `:4853`, `:4855`-`4856`)
   is a bare assignment with no existence check. If two distinct physical columns
   on the *same* element normalize to the same key (e.g. captions `"Order-ID"` and
   `"Order_ID"`, or two columns differing only by a character the whitespace-only
   normalization ignores), the later one silently wins and the earlier column's
   id becomes unreachable by name. Inference that resolves a match via
   `candidateNames`/`hasCol` could therefore resolve to the *wrong* physical
   column's id on one side, with no signal that a collision occurred. Task 2
   should consider detecting this at candidate-set build time (e.g. track and warn
   when a normalized name maps to more than one raw column on the same entry)
   rather than trusting a single winner.

2. **A name that exists on both sides but is not actually a key.** Generic
   columns like `NAME`, `CREATED_AT`, `UPDATED_AT`, `STATUS`, or a bare `ID` are
   plausible to find on *both* a fact and a dimension table by pure name-match,
   without being the intended join key. The plan's own safety argument — that
   inferred keys flow into `join-plan.json` where gate 16's warehouse uniqueness
   probe validates them before GREEN — only catches **fan-out** (the dimension
   side isn't unique on the inferred key). It does **not** catch a
   coincidentally-unique-but-semantically-wrong match (e.g. both sides happen to
   have a unique `CREATED_AT` timestamp): that would pass the uniqueness probe and
   produce a confidently-wrong join. Task 2 should not treat "name matches on both
   sides" alone as sufficient confidence — consider a stoplist of common non-key
   column names, a preference for names that look key-shaped (`*_ID`, `*_KEY`, or
   equal to the target table's clean name + `_ID`), and/or making every
   name-inferred match highly visible in `warnings`/`relationshipCoverage` for
   human review rather than silent auto-acceptance.

3. **The "take ALL matches as a composite key" instruction can over-constrain the
   join.** The plan directs that when more than one name matches, all of them
   become a composite key (replicating Tableau's own auto-match behavior). But if
   an incidental non-key column (e.g. `NAME` or `CREATED_AT`) matches *in addition
   to* the true key, the resulting composite key is narrower than intended: rows
   that should join (matching on the real key) will silently fail to join if the
   incidental column happens to differ (e.g. two customer records created at
   different times). This is an **under-join** (rows silently dropped), the
   opposite failure mode from fan-out, and gate 16's uniqueness probe — which only
   checks cardinality on the key that *was* chosen — cannot detect it, because a
   narrower composite key is, if anything, *more* likely to look unique. Task 2
   should weigh excluding low-signal column names from candidacy before applying
   the "take all matches" rule, or at minimum flag any composite key with more
   than one component prominently rather than treating it as equally trustworthy
   to a single strong match.

4. **`entry.element.columns` reflects what Tableau serialized, not necessarily
   every column physically in the warehouse table.** If Tableau never discovered
   or referenced a particular warehouse column (so it never got a
   `<metadata-record>` or a `<columns><column>` entry), that column is invisible
   to both `colIdMap` and `candidateNames` — inference cannot find a key that was
   never serialized at all, even if the warehouse actually has one. This is a
   ceiling on recall, not a wrong-match risk, but Task 2's warnings/coverage
   should distinguish "no matching name found" from "found and wired" so an
   operator knows when manual authoring is still required.
