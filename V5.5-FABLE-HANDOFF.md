## W2.1 — Filter-literal existence probe  (HIGH value; diagnostic accelerator)

**Failure it addresses:** the primary cause of the field-run blanking — a
control default value `"Region A & B"` that no row carries (the DM calc
emitted `"Region A and B"`), and Top-3 list filters `["2015"]` against a
`TIMESTAMP` column. W1.1 already turns this RED at verification (empty tiles); W2.1
catches the CAUSE earlier and names the exact literal + near-miss, which is what
saves the ~30 min of no-data hunting.

**Spec:** a new `scripts/probe-filter-literals.rb --workbook-id <id>
[--workbook-spec <spec>] --out filter-probe.json`:
1. From the live/loaded workbook spec, enumerate every (column, literal) filter
   condition: (a) control default `value`/`values` + the column each control
   `filters` targets (walk `filters[].{source.elementId, columnId}`); (b) every
   element `filters[]` of `kind:"list"` with literal `values`.
2. Resolve each `columnId` to the underlying column/formula and the element that
   owns the UNFILTERED domain (the feeder/base table — the `masterAll`-style twin,
   NOT the filtered `master`). Query its DISTINCT domain (Sigma element export of
   the unfiltered source, or a `SELECT DISTINCT` via the sigma query API).
3. For each literal, check membership in that domain. Miss → report with
   edit-distance near-misses (`"Region A & B"` ≈ `"Region A and B"`,
   distance 3) and the column.
4. **Degrade to a WARNING, never a hard stop, when the column can't be resolved**
   — W1.1's emptiness gate is the hard teeth; W2.1 is the pointer. This keeps
   corpus false-positive risk at zero.

**Anti-overfit note:** the near-miss heuristic (edit distance, `&`↔`and`,
case/space normalization) is generic string logic, not workbook-specific. The
date-part case (`["2015"]` vs timestamps) generalizes to "a list literal that
parses as a bare year/number against a temporal/numeric column" — grammar-level,
not fixture-level.

## W2.2 — Typed-literal calc lint  (HARD; .twb grammar + Sigma formula semantics)

**Failure it addresses:** the post-fix cause the field run never diagnosed —
converter calcs `If([Year] = "2014", [Unit Value])` where `Year` is NUMBER compile
clean and render NULL for every measure; same for a date-part filter emitted as a
string list against a `TIMESTAMP`.

**Spec:** a lint over the generated DM/workbook formulas (a new lint in
`scripts/lib/`, wired into the existing calc-lint path):
- Detect a comparison/equality between a column KNOWN numeric/temporal (from the
  landed warehouse schema or the Sigma column type) and a STRING literal. Tableau's
  `YEAR()`/`DATEPART` produce integers; a converter that renders `YEAR([Date]) =
  2015` as a string `"2015"` comparison is the bug class.
- Emit a hard lint finding + an auto-coercion suggestion (`Number([Year]) = 2014`
  or a real `DatePart`/`DateTrunc` predicate / a derived year column).
- Must consult the ACTUAL column type (landed schema or live `/columns`), not guess
  from the name — a string column literally named "Year" must NOT be coerced.

**Why Fable:** correctly distinguishing "numeric column compared to a string
literal that should be numeric" from legitimate string comparisons needs real
type-resolution + Sigma formula-grammar reasoning, and the auto-coercion must be
provably type-safe. A hasty version risks rewriting valid formulas (corpus
regressions). Derive strictly from the .twb calc grammar + the resolved column
type; zero fixture literals.

## Review-surfaced residual holes (NEW — close these; all are false-NEGATIVES)

The adversarial review confirmed the shipped W1.1 export-based emptiness gate is
false-positive-free and catches the field-run class. It also proved two narrow
residual holes that the export-based approach structurally cannot close — both are
false-negatives (a dataless tile could slip), neither reddens a healthy workbook.
The primary fix for BOTH is **W1.7** (render-side per-tile blank detection), which
is blind to how an export is classified. Verify each with the repro, then close.

- **RH-1 — dual-role displayed TABLE in an artifact-less run.** When NO build
  artifacts exist (`parity-plan.json` / visual-verify manifests absent), the census
  falls back to the leaf heuristic and classifies `is_feeder = referenced &&
  kind=='table'`. A displayed TABLE that is ALSO sourced by another tile (referenced,
  kind table) is therefore treated as a feeder and its emptiness is NOT gated. The
  round-2 fix closed this for referenced CHART/KPI tiles (non-table), but a
  displayed dual-role TABLE remains. **Why it is narrow:** every REAL migration
  carries a `parity-plan.json` (build-parity-plan.rb runs in Phase 6), which
  declares displayed tiles explicitly and bypasses the leaf heuristic — so this
  only bites offline/standalone `verify-anchors` runs. **Repro:** a spec with a
  table `T` (empty export) that another tile sources via `source.elementId: T`, NO
  parity-plan.json in the workdir → `verify-anchors` exits 0 with `T` displayed=false.
  **Close via:** (a) W1.7 render-side blank check (definitive), and/or (b) page-aware
  classification — an element on a DASHBOARD page (not a hidden data/feeder page) is
  displayed regardless of the source graph. Do NOT just "check all tables" (a
  legitimately-empty undisplayed staging table would false-RED).

- **RH-2 — export-FAILED tiles are excluded from emptiness.** `dashboard_tiles_empty`
  counts only `data_rows == 0`; a tile whose export FAILED (HTTP error / HTML-behind-200
  / timeout → `data_rows == nil`) is NOT flagged. This is the correct choice for
  false-positive avoidance (a transient export failure must not redden a healthy
  workbook), but a GENUINELY broken tile that ALWAYS fails to export is a blind spot.
  **Close via:** W1.7 render-side check (a broken tile renders blank regardless of
  export status), OR a bounded retry + a distinct `dashboard_tiles_export_failed`
  report that WARNs (not fails) so a persistent failure is at least surfaced. Keep it
  advisory to preserve the no-false-positive property.

(Not a hole, for the record: the all-embedded ORACLE path already fails closed on a
missing `tiles_all_nonempty` field; only the general gate-13 path grandfathers a
stale pre-W1.1 verdict, with a loud [WARN] to re-run verify-anchors.)
